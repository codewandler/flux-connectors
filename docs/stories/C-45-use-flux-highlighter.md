# Render Flux to SVG and PNG using flux's own highlighter

## Goal
Replace the ad-hoc regex highlighter with flux's real one, so rendered Flux is coloured by the same
CST classification the language itself uses and cannot drift from the grammar.

## Acceptance
- [ ] Rendering uses **`flux_lang::highlight::highlight(src) -> Vec<(TextRange, HighlightClass)>`**.
      It is public in the pinned `codewandler-flux-lang` 0.37, so this needs **no new dependency**.
- [ ] `scripts/flux-to-svg.py` is deleted. Its regex keyword list duplicates knowledge flux owns and
      would drift silently.
- [ ] **SVG** output, with light and dark palettes, replacing `assets/readme-snippet-*.svg`
      byte-for-byte in role.
- [ ] **PNG** output supported too — see Notes for the two routes; pick one and say why.
- [ ] Rendering is wired into the build so the README asset is a **checked artifact**, not something
      regenerated by hand. This is the gap the current script explicitly leaves open.
- [ ] A test asserts the rendered SVG covers every `HighlightClass` the snippet contains, so a new
      class added upstream shows up as a failure rather than as uncoloured text.

## Notes
- **flux already does all of this, which the regex script did not check for.** The substrate is
  `flux_lang::highlight` — a walk over the lossless CST that classifies each token by kind *and its
  parent node's kind*, so `when` is a keyword because of where it sits, not because it is on a list.
  Its own doc comment calls keyword-list matching "strictly less accurate", and notes the classifier
  is **total**: malformed source still yields spans.
- **`HighlightClass`**: `Keyword`, `Op`, `Var`, `Annotation`, `String`, `Number`, `Comment`, `Punct`,
  `Type`, `Error`. The regex script had no `Annotation`, no `Op`/`Type` distinction, and no `Error`.
- **flux renders both formats already.** `flow_render` (`../flux/crates/flux-tools/src/render.rs`)
  is an SVG source view over the same `highlight` walk, and flux-tools has a `png` feature
  (resvg/usvg/tiny-skia/fontdb) behind `flux render -o out.png`.
- **Two routes for PNG, both legitimate:**
  1. **Shell out to `flux render -o out.png`** — zero dependencies here, but adds a build-time
     dependency on the flux binary being installed.
  2. **Take `resvg`/`usvg` directly** in `connector-cli` — self-contained, but a heavy dependency
     tree for one README image, and flux-tools pins the four crates as a coupled set.
  Recommendation: SVG natively via `flux_lang::highlight` (no dependency), PNG via route 1 and
  skipped with a clear message when flux is absent. GitHub renders SVG fine, so PNG is a convenience.
- **Do not depend on `flux-tools`** to get `flow_render`: it is a high-layer crate pulling tokio and
  much else, and `AGENTS.md` records that this repo depends on `flux-lang` and nothing else of flux's.
