# Render Flux to SVG and PNG using flux's own highlighter

## Goal
Replace the ad-hoc regex highlighter with flux's real one, so rendered Flux is coloured by the same
CST classification the language itself uses and cannot drift from the grammar.

## Acceptance
- [x] Rendering uses **`flux_lang::highlight::highlight(src) -> Vec<(TextRange, HighlightClass)>`**.
      It is public in the pinned `codewandler-flux-lang` 0.37, so this needs **no new dependency**.
- [x] `scripts/flux-to-svg.py` is deleted. Its regex keyword list duplicates knowledge flux owns and
      would drift silently.
- [x] **SVG** output, with light and dark palettes, replacing `assets/readme-snippet-*.svg`
      byte-for-byte in role.
- [x] **PNG** output supported too — see Notes for the two routes; pick one and say why.
- [x] Rendering is wired into the build so the README asset is a **checked artifact**, not something
      regenerated by hand. This is the gap the current script explicitly leaves open.
- [x] A test asserts the rendered SVG covers every `HighlightClass` the snippet contains, so a new
      class added upstream shows up as a failure rather than as uncoloured text.

## Progress
- Done. `connector_flux::highlight` renders the SVG from `flux_lang::highlight::highlight`;
  `connector-cli`'s `pipeline::plan` emits both palettes as planned artifacts on a full run (like
  `site/catalog.json`), so `build` writes them, `diff` reports them stale and the whole-repo
  fixed-point assertion covers them. PNG is **route 1**: `build --png` shells out to
  `flux render -o …png`, skipping with a message when the binary is absent. Route 2 would have
  needed a fenced manifest edit for a convenience image.
- **Found while doing it — worth a flux-side story.** flux-lang 0.37's highlighter is written
  against `flow` declarations and does not cover **composite `op` declarations**, which is all this
  repo emits. Its parser gives an `op` distinct node kinds (`OP_DECL`/`OP_HEADER`, and `OP_META` for
  the `description`/`risk`/`idempotency`/`effects`/`limits`/`expose`/`view` lines), and
  `highlight.rs`'s tables list only the `flow` spellings: `keyword_leads` has `FLOW_HEADER` but not
  `OP_HEADER`/`OP_META`, and `name_class`'s type-reference arm has `PARAM | FLOW_HEADER | BIND_STMT
  | MEMO_STMT | NAME` but not `OP_HEADER`. Consequences in the committed image: the leading `op`,
  the operation's own name and the six metadata keywords classify as `Punct`, and the **return**
  type classifies as `Op` while a parameter's type classifies as `Type`.
- So the new image is **less colourful than the regex script's was** — the script simply asserted
  that `op` and `description` are keywords. Reproducing that assertion here would rebuild exactly
  what this story deletes, so it renders what flux actually knows. The fix is a few table entries in
  flux-lang; this repo is its most affected consumer. `flux render --view=source` on the same file
  shows the same flat header, so the gap is flux's own doc images too, not this renderer's.

## Notes
- **flux already does all of this, which the regex script did not check for.** The substrate is
  `flux_lang::highlight` — a walk over the lossless CST that classifies each token by kind *and its
  parent node's kind*, so `when` is a keyword because of where it sits, not because it is on a list.
  Its own doc comment calls keyword-list matching "strictly less accurate", and notes the classifier
  is **total**: malformed source still yields spans.
- **`HighlightClass`**: `Keyword`, `Op`, `Var`, `Annotation`, `String`, `Number`, `Comment`, `Punct`,
  `Type`, `Error`. The regex script had no `Annotation`, no `Op`/`Type` distinction, and no `Error`.
- **flux renders both formats already.** `flow_render` (`../flux/crates/flux-tools/src/render.rs`)
  is an SVG source view over the same `highlight` walk, and flux-tools has a `png` feature
  (resvg/usvg/tiny-skia/fontdb) behind `flux render -o out.png`.
- **Two routes for PNG, both legitimate:**
  1. **Shell out to `flux render -o out.png`** — zero dependencies here, but adds a build-time
     dependency on the flux binary being installed.
  2. **Take `resvg`/`usvg` directly** in `connector-cli` — self-contained, but a heavy dependency
     tree for one README image, and flux-tools pins the four crates as a coupled set.
  Recommendation: SVG natively via `flux_lang::highlight` (no dependency), PNG via route 1 and
  skipped with a clear message when flux is absent. GitHub renders SVG fine, so PNG is a convenience.
- **Do not depend on `flux-tools`** to get `flow_render`: it is a high-layer crate pulling tokio and
  much else, and `AGENTS.md` records that this repo depends on `flux-lang` and nothing else of flux's.
